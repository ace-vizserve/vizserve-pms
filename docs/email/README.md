# The email shell

Every email this app sends — all twelve of them — is one layout: `lib/email/layout.ts`.

There is **no dashboard-hosted template**, in Resend or anywhere else. The
Resend adapter (`lib/email/transports/resend.ts`) hands the API a rendered
`html` and `text` pair built from `EmailBody`, which means the markup is
reviewed in this repo, diffed in this repo, and cannot be edited out from under
the code by somebody in a web UI. That was one of the stated reasons for picking
Resend over the EmailJS arrangement it replaced, where a hand-pasted template
lived in a browser and nowhere else.

**So there is nothing to create in the Resend dashboard.** If a stored template
is ever wanted there anyway — for a broadcast, say, which is a different job
from transactional mail — it is a copy of this output and it will drift from it.

## Previewing

```bash
npm run test -- tests/email/preview.test.ts
```

Writes `preview-*.html` and `preview-*.txt` beside this file; open the HTML in a
browser. They are regenerated by any `npm test` run and are **gitignored** —
generated output, not source.

What a browser preview cannot tell you is how **Outlook** renders it. Outlook
draws through Word, and it is the client most likely to break a layout. Send one
real message before trusting a change:

```bash
EMAIL_TEST_RECIPIENT=you@yourdomain.com npm run email:test
```

## The design

It is **the app's own surface, rebuilt in table HTML** — not a template in the
brand colours. A `Card` in `components/ui/card.tsx` is `rounded-lg border
bg-card grade-surface shadow-raised-lg`: a white panel, graded top to bottom,
with a hairline border and a soft cast, sitting on the cool-grey
`--background`. The email reproduces all four.

> **The first cut got this backwards**, and it is the easy mistake to make.
> It followed react-email's [`01-Barebone`
> demo](https://github.com/resend/react-email/tree/canary/apps/demo/emails/01-Barebone)
> literally — a tinted panel sunk *into* a white card — which reads as a well
> carved into the surface. The design system bans exactly that: *"No inward
> emboss. Ever… Things sit ON the page, never in it."* **Grey goes under white,
> never inside it.**

What Barebone is still owed is the outer proportions: one centred 640px column,
the lockup above the panel, generous padding. Borrowed as **markup, not as a
dependency** — the demo is JSX over `react-email` components plus a Tailwind
config, neither of which exists here, and both of which would have to render at
send time.

### The parts that make it read as this app

| | |
|---|---|
| **Panel** | white + `--gradient-surface` + 1px `--border` + `--elev-2`, on the grey ground |
| **Status chip** | the `TONE` map from `components/status-badge.tsx` — subtle fill, own border, solid text, leading dot, `rounded-md`, 28px, 12px semibold |
| **Button** | `--gradient-primary` over `--brand`, `rounded-md`, 40px — the app's control height |
| **Lockup** | the blue `rounded-md` tile and white mark from `BrandLockup`, with "Team Portal" beneath the wordmark |
| **Quote block** | flat: a `--muted` fill and a border, no shadow. Depth is outward only |
| **Type** | 24px heading, 16px body at `-0.005em`, 13px meta, 12px fine print |

The chip carries its **dot and its label**, so state survives greyscale, a
screenshot and a printed queue — and the label is repeated in the text part,
which has no colour at all. Labels are human wording (`Awaiting review`), never
the enum (`PENDING_REVIEW`).

Two departures from Barebone beyond the inversion, both deliberate:

- **No social row, postal address or unsubscribe line.** Everything here is
  transactional. An unsubscribe link on the Gate 3 email invites the one client
  whose reply Phase 4 depends on to switch it off. `docs/12-ui-and-notifications.md` §3
  is that budget; this is the same argument one level down.
- **No centred hero.** Every body opens "Hi Maria," and most carry a label/value
  table. Centred copy above a left-aligned facts grid reads as a broken
  template rather than a considered one.

## Colours

The demo's tokens, swapped for the app's own from `app/globals.css`. No email
client can read a CSS custom property, so the values are **resolved to literals
in `layout.ts` and nowhere else** — a hex at a call site is how a palette drifts
one email at a time.

| Barebone | Token | Value | Contrast |
|---|---|---|---|
| `bg-2` `#F3F4F6` | `--background` | `#F5F7FA` | the ground the panel sits on |
| `bg` | `--card` | `#FFFFFF` | the card |
| `fg` `#14171E` | `--foreground` | `#0F1626` | headings |
| `fg-2` `#43454B` | `--foreground-muted` | `#556074` | 6.25:1 on white |
| `fg-3` `#7B7D81` | `--muted-foreground` | `#656F82` | 5.06:1 on white |
| `stroke` | `--border` | `#E3E7EE` | hairlines |
| — | `--muted` | `#F0F3F7` | flat blocks (the quote) |
| — | `--gradient-surface` | `#ffffff → #fafcfd` | the panel's grade |
| — | `--gradient-primary` | `#5169b4 → #3b4f94` | the button's fill |
| `brand` `#614500`, button `bg-fg` | `--brand` | `#4359A5` | white on it, 6.54:1 |
| Inter | `--font-sans` | Figtree, system stack behind it | |

`#5BC0DE` appears in no text role. It is 2.09:1 against white in **both**
directions — surface only, and there is no surface here that needs it.

The face is named but will not load in Gmail or Outlook, which is the expected
outcome rather than a failure: the type **scale** does the work, not the face.

## Dark mode

The email **opts out** (`color-scheme: light`). The app has a real dark theme and
an email cannot use it, so it does not pretend to: Gmail and Outlook recolour an
unlabelled message by guessing, and a guessed palette puts grey text on a grey
panel more often than it gets it right. The status chip is where that does the
most damage — an inverted fill with un-inverted text is how a status becomes
unreadable in the one message that exists to convey it.

## Two things that look like decoration and are not

- **The wordmark is text beside the mark, not part of the image.** Outlook and
  Gmail block remote images by default, and an identity that vanishes with the
  images is what makes a client read an approval request as phishing.
- **The button is a table cell carrying the fill with the anchor inside it.**
  Outlook drops padding on an inline anchor, which turns the one thing the email
  exists for into a line of blue text.

## Where the words live

Not here. Subjects, bodies **and chips** are in `lib/email/client-emails.ts`
(the eight client-facing sends) and `lib/email/dispatch.ts` (the per-type
presentation for the notification outbox). This file is the shell they render
into.

### Which chip each email carries

| Email | Chip |
|---|---|
| Request received | Awaiting review · `warning` |
| Approved, under way | Approved · `success` |
| We need a bit more | Returned · `info` |
| Not able to take this on | Rejected · `danger` |
| Ready for your approval, and both reminders | Awaiting your approval · `warning` |
| How did we do? | Completed · `success`, or **Closed without a response** · `neutral` |
| `pending_approval` | Awaiting your approval · `warning` |
| `assigned` | Assigned to you · `brand` |
| `qa_requested` | Ready for QA · `warning` |
| every other notification type | **none** |

Two of those are rules rather than choices:

- **The two completions must not look alike** (design system §4.1). `COMPLETED`
  means the client approved; `COMPLETED_NO_RESPONSE` means the clock ran out and
  nobody looked — and the feedback request is the one email that reaches
  somebody who may never have seen the approval. A green "Completed" there
  claims an approval they did not give. `tests/unit/email-status-chip.test.ts`
  pins it.
- **Most notification types get no chip.** A notification row carries a title, a
  body and a link — no status column — so for `client_decision` or
  `status_changed` any chip would be invented. The row does not say whether the
  client approved or rejected, and a confident guess in the app's own chip is
  worse than no chip, because the app's chips are otherwise trustworthy.

The chips are **written beside the copy, not read off a status enum**, and that
is deliberate. `REQUEST_STATUS` in `components/status-badge.tsx` stays the only
place a status becomes a colour *in the app*; it is a React module that pulls in
lucide and does not export its map, and reaching into it from a `server-only`
mailer would drag a component tree across the boundary to win four strings. The
deeper reason is that these chips are not always the record's status — the Gate
3 email goes out while the task reads `FOR_CLIENT_APPROVAL`, which means nothing
to a client; what they need to see is that we are waiting on *them*. Where the
wording does correspond to a status the team can see, it is deliberately the
same word.
